# ADR 0003 — E2EE for 1:1 direct chats

**English** · [Español](../es/adr/0003-e2ee-1to1.md) · [Italiano](../it/adr/0003-e2ee-1to1.md)

Implemented in the local TUI and checked in CI. `crypto/` runs Olm; `pkg/secureclient` integrates identity, messaging and the encrypted archive. Legacy invitations and remote TUI are outside these guarantees. See the [verification matrix](../verification.md). Karatty has no independent audit.

## Context and decision

The alpha supports only 1:1 direct chats from a TUI running on the user's device. Forward secrecy is required: stealing an identity key or current session state must not derive already-deleted keys for earlier messages stored by the server.

Use **Olm 1:1 with Double Ratchet**, through Rust [vodozemac](https://github.com/matrix-org/vodozemac) 0.11.2, built into the local client package. Its [API](https://docs.rs/vodozemac/0.11.2/vodozemac/olm/index.html) documents asynchronous sessions, one-time keys and per-message encryption. The library has a [public audit](https://matrix.org/blog/2022/05/16/independent-public-audit-of-vodozemac-a-native-rust-reference-implementation-of-matrix-end-to-end-encryption/); that audit does not audit this integration or automatically cover later versions. We select `SessionConfig::version_1()`. Its 8-byte MAC is a known limitation; [Olm v2 is documented as experimental](https://github.com/matrix-org/vodozemac/blob/main/CHANGELOG.md). No custom Go ratchet is implemented.

## Identities and establishment

- Each installation generates an Olm Ed25519/Curve25519 identity and Curve25519 one-time keys locally. Its SSH Ed25519 identity signs the Olm identity and account ID with version/domain separation. The client checks the signature and pins its peer before opening a session. The server distributes public keys and atomically consumes one-time keys; it receives no private keys. One-time keys are signed by the Olm identity. There is no reusable fallback key: exhausted one-time keys require the recipient to replenish them before a new session starts.
- The TUI exposes a fingerprint covering both identities and requires verification for a new contact or changed identity. Participants must compare through another trusted channel to detect first-contact server substitution. Without it, first contact is not authenticated against a malicious server. Identity changes halt sending and require explicit re-verification; they are never silently accepted.
- One active device per account is supported. Recovering with an offline code/new SSH key does not recover an Olm identity or lost local history. The previous identity is revoked and the contact must verify the replacement. The recovery code is not a decryption key.

## Messages and durable local state

- Encryption happens before sending and decryption after receiving. The API accepts only versioned Olm-shaped direct-chat envelopes, validates structure/version/limits and stores opaque data. Plaintext `body` contracts and a server-side TUI are excluded from alpha messaging. A modified client may still place text inside a field labeled ciphertext; the server cannot cryptographically prove correct sender encryption. Guarantees refer to the official client and complete-flow tests.
- Envelopes contain a Karatty protocol version, Olm message type, session ID, sender identity and ciphertext. The encrypted inner payload binds conversation, sender and client ID. Server-assigned sequence/time are **not E2EE-authenticated metadata**. The client validates structure/order and clamps future archive timestamps, but cannot prove the server did not hide or reorder deliveries through metadata. Active storage and backups contain envelopes plus delivery metadata.
- Ratchet state, one-time keys and outbox remain **on the local device**. Sending atomically persists the advanced ratchet with the envelope/client ID before transmission; retry sends that exact envelope. Receiving atomically saves ratchet advancement, readable local-archive entry and processed sequence before exposing plaintext to the UI. A file lock prevents two processes from sharing state. Operations must tolerate interrupted power, lost responses, duplicate events and out-of-order messages without key reuse. Physical power-loss behavior on all filesystems has not been tested.
- History needs a locally encrypted copy under an archive key independent of SSH/Olm identity keys. A passphrase is entered when opening the client; Argon2id derives the key and AEAD encrypts the archive. Stealing only an SSH key or current ratchet must not open it. Client purging at 30 days is tested; old ratchet keys are not retained to decrypt server copies again.

## Scope of forward secrecy and retention

Forward secrecy covers earlier messages **whose message keys have been deleted** against later theft of identity/current-ratchet state. It does not protect text on screen, an unlocked local copy, a snapshot taken before deletion, an actively compromised device or delivery metadata. Initial identity substitution permits interception until participants compare fingerprints. Account recovery does not promise old-content recovery.

Thirty-day retention applies to envelopes, identifiers and active local copies. Cleanup only runs while the client is used; offline devices and third-party snapshots cannot be remotely erased. The future hosted-service policy allows at most seven additional days in encrypted backups, subject to operational verification; the local guide configures no automatic backups. Rotation, account deletion and local cleanup must also be tested with restores/retries.

## Acceptance criteria and continuing checks

1. Two clean installations: registration, consent, verified fingerprints, bidirectional exchange, disconnect/restart/retry and out-of-order reception.
2. Alter identity, envelope, conversation, sender, ID and version; authenticated-field failures must be visible. Check sequence structure/order without claiming cryptographic authenticity for server metadata.
3. Advance the ratchet/delete keys, then show server copies plus current identity/ratchet cannot decrypt consumed messages. Test lost state, recovery and identity changes.
4. Inspect HTTP/WSS, PostgreSQL, logs and backups for readable test messages; verify archive encryption/expiry.
5. Windows/Linux/macOS CI and packages with pinned vodozemac, third-party licenses and download verification.

`--public-signup` defaults to loopback. Non-loopback listeners require `--public-network`, TLS and no remote TUI. A future hosted service still needs the operational/operator checks in [release](../release.md) and [operations](../operations.md). The released local alpha does not claim two-physical-machine LAN verification.
