# ADR 0003: E2EE de los directos 1:1

Estado: decisión de diseño aceptada el 2026-11-01; existe una prueba aislada del ratchet en `crypto/`, **sin integrar** en el cliente ni en la API. Ningún mensaje de la versión actual tiene estas garantías.

## Contexto y decisión

La alpha pública permitirá solo directos 1:1 desde una TUI que se ejecuta en el equipo del usuario. El usuario exige secreto futuro: robar hoy una clave de identidad o el estado actual de una sesión no debe permitir derivar las claves ya borradas de mensajes anteriores almacenados por el servidor.

Se usará **Olm 1:1 con Double Ratchet**, mediante la biblioteca Rust [vodozemac](https://github.com/matrix-org/vodozemac), fijada a una versión concreta y compilada como parte del cliente. La API [documenta](https://docs.rs/vodozemac/0.11.1/vodozemac/olm/index.html) sesiones asíncronas, claves de un solo uso y cifrado por mensaje; la biblioteca cuenta con una [auditoría pública](https://matrix.org/blog/2022/05/16/independent-public-audit-of-vodozemac-a-native-rust-reference-implementation-of-matrix-end-to-end-encryption/). Se elegirá `SessionConfig::version_1()`, la versión estable del protocolo. Su MAC de 8 bytes es una limitación conocida; [Olm v2 sigue siendo experimental](https://github.com/matrix-org/vodozemac/blob/main/CHANGELOG.md). No se implementará un ratchet propio en Go. La integración con el cliente Go y los binarios multiplataforma forman parte de la implementación pendiente.

## Identidades y establecimiento

- Cada instalación tendrá una identidad Olm Ed25519/Curve25519 y claves Curve25519 de un solo uso generadas localmente. La identidad de autenticación SSH Ed25519 firmará, con separación de dominio y versión, la identidad Olm y el identificador de cuenta. El cliente comprobará esa firma y fijará la identidad del contacto antes de crear una sesión. El servidor podrá distribuir claves públicas y consumir una clave de un solo uso de forma atómica; no recibirá claves privadas. Las claves de un solo uso también estarán firmadas por la identidad Olm. No habrá clave de reserva reutilizable en la alpha: si se agotan las claves de un solo uso, iniciar una sesión nueva deberá esperar a que el destinatario reponga claves.
- La TUI mostrará una huella de verificación de ambas identidades y exigirá confirmación al iniciar un directo o cuando cambie la identidad. Los participantes deberán comparar la huella por otro medio para detectar un servidor que sustituya claves en el primer contacto. Sin esa comparación, el primer contacto no está autenticado frente a un servidor malicioso. Cambios de identidad detendrán el envío y requerirán nueva verificación; nunca se aceptarán silenciosamente.
- Cada cuenta tendrá un solo dispositivo activo en la alpha. Recuperar acceso con el código y una nueva clave SSH no recupera la identidad Olm ni el historial cifrado si se perdió el estado local; debe revocar la identidad anterior y requerir una nueva verificación del contacto. El código de recuperación no será una clave de descifrado.

## Mensajes y estado

- El cliente cifrará antes de enviar y descifrará después de recibir. La API aceptará exclusivamente un sobre versionado de Olm en directos; el servidor validará estructura, versión y límites, y guardará el sobre como dato opaco. El contrato `body` de texto en claro y la TUI ejecutada en el servidor no pueden usarse en el servicio público. Un cliente modificado todavía podría enviar texto en un campo que llama cifrado: el servidor no puede demostrar criptográficamente que el remitente cifró correctamente. Las garantías se refieren al cliente oficial y a las pruebas del flujo completo.
- El sobre incluirá la versión de Karatty, el tipo de mensaje Olm, el ID de sesión, la identidad del remitente y el texto cifrado. El texto cifrado incluirá y comprobará la conversación, el remitente y el ID de cliente para impedir reubicar un sobre entre conversaciones. La secuencia y la fecha las asigna el servidor después del cifrado; son metadatos de transporte no autenticados por E2EE y no se usarán para tomar decisiones de seguridad. La base y los respaldos solo conservarán sobres y metadatos de transporte.
- El estado del ratchet, las claves de un solo uso y la cola de salida vivirán **solo en el equipo local**. El envío guardará atómicamente el ratchet avanzado junto al sobre e ID de cliente antes de transmitir; un reintento enviará exactamente el mismo sobre. La recepción guardará atómicamente el ratchet avanzado, el texto descifrado en el archivo local y la secuencia procesada antes de confirmar la entrega a la interfaz. Un bloqueo de archivo impedirá usar el mismo estado desde dos procesos. Las operaciones deben tolerar cortes de energía, respuestas perdidas, eventos duplicados y mensajes fuera de orden sin reutilizar claves.
- La vista de mensajes históricos necesitará una copia local cifrada con una clave de archivo independiente de la clave SSH y de la identidad Olm. El usuario aceptó una frase secreta local que se introduce al abrir el cliente. La clave se derivará mediante Argon2id y cifrará el archivo con AEAD. Robar solo la clave SSH o el estado ratchet actual no debe abrir ese archivo. La purga a los 30 días debe probarse junto con el cliente; no se conservarán claves antiguas del ratchet para volver a descifrar la copia del servidor.

## Alcance de la garantía

El secreto futuro protege mensajes anteriores **cuyas claves de mensaje ya fueron borradas** frente al robo posterior de la clave de identidad o del estado actual del ratchet. No protege el texto ya visible en pantalla, una copia local desbloqueada, una captura hecha antes del borrado, un dispositivo comprometido mientras se escribe, ni los metadatos que el servidor necesita para entregar mensajes. Una identidad inicial sustituida por el servidor permite un ataque de intermediario hasta que las personas comparen huellas. La recuperación de una cuenta no promete recuperar contenido anterior.

La retención de 30 días aplica a sobres, identificadores y copias locales; los respaldos cifrados pueden retenerlos como máximo 7 días adicionales, según la decisión del usuario. La rotación de claves, la eliminación de cuenta y el borrado de datos locales se verificarán también frente a restauraciones y reintentos.

## Criterios de aceptación antes de publicar

1. Prueba interoperable con dos instalaciones limpias: registro, consentimiento, huellas verificadas, mensajes en ambas direcciones, desconexión, reinicio, reintento y recepción fuera de orden.
2. Prueba de manipulación de identidad, sobre, conversación, remitente, secuencia y versión; todo cambio debe producir error visible y detener el envío cuando corresponda.
3. Prueba de secreto futuro: tras avanzar y borrar claves antiguas, una copia del servidor más la identidad y el ratchet actuales no descifra mensajes anteriores. Probar también pérdida de estado, recuperación y cambio de identidad.
4. Inspección de HTTP/WSS, PostgreSQL, logs y respaldos: el mensaje de prueba no debe aparecer en claro. Comprobar el cifrado y vencimiento de la copia local.
5. CI y artefactos para Windows, Linux y macOS con la misma versión fijada de vodozemac, licencias de terceros y verificación de la descarga.

Hasta cumplirlos, `--public-signup` seguirá restringido a loopback y el repositorio no se anunciará como una alpha E2EE.
